MDL 验证台账

在 Cortex-M4 上不重新烧录地更换 MCU 功能，用 MPU 把模块关进沙箱， 对标 LuaTOS / MicroPython 但不付出解释器的代价。

这张表的主轴不是"做完了多少"，而是哪些结论是在真机上验过的。 本项目的规矩是：编译通过不算完成。因此状态分「已验证」（真机跑过） 与「完成」（代码就位、尚未在硬件上证明）两级，并且一个多日未复跑的结论 不会被当作现在仍然成立。

# 任务 优先级 状态

外设能力

MDL 对任何外设寄存器都没有 MPU 区域——这正是沙箱的价值所在。每一次传输都是一次 受控调用，host 逐次校验「这条总线是你声明的」和「这个缓冲区在你自己内存里」。

关于那些「未实测」。 LuaTOS 和 MicroPython 的性能数字没有在本项目里测过，所以表里 不给它们具体数值——凭印象填一个量级进去，正好会毁掉这张表唯一的价值。 表中关于它们的描述只涉及结构性事实（解释执行、有 GC、无 MPU 边界）， 那些不需要测量也成立。

它们赢在哪里也照实写。最后三行不是客套： Lua 和 Python 改完直接跑，MDL 要在主机上过一遍工具链； 它们能同时驻留多个模块，我们目前一次只能跑一个； 它们有成熟的库，我们的每个外设驱动都是一行行写出来的。 这个方案的适用条件是「性能和确定性值得付出工具链的代价」—— 不满足这个条件时，它们是更好的选择。

模块是原生代码，不是字节码。两条线之差就是循环体本身的开销。

代价集中在闸口

沙箱的成本不是连续摊在每条指令上，而是一次性付在每次 host 调用上。

受控 host 调用213.57 cycles
折合时间≈ 0.74 µs
含提权、参数校验、指针归属检查与降权返回。 所以 ABI 的设计取向是少而粗的调用，而不是多而细的。
中断 → 非特权 handler · 308 样本

派发延迟

ISR 运行在特权态，所以它只做两件事：记录事件、唤醒模块任务。 MDL 自己的 handler 稍后在那个任务里非特权地跑。

最快1.7 µs
平均4.6 µs
最慢5.9 µs
这是诚实且不可回避的代价：事件经过一次任务唤醒和上下文切换才到达 MDL， 不是中断延迟。比这更紧的时限做不到，改 ABI 也没用—— 那种活必须是 host 代码。

未结项

按"挡住什么"排序，不按工作量。

  • H10 的 QEMU 那半受阻
    PendSV 那个 bug 已由 AT32 间接答完（共用同一份 port.c 与 module_task.c）。剩下的是可移植性回归。 QEMU 其实装着，但和原生 gcc.exe 一样被 Windows 应用控制策略拦掉（退出码 0xC0E90002）——需要在本机放行。
  • S4 的拒绝路径没跑过完成
    两个 MDL 用同一个命令名会被拒——代码写了，真机上没触发过， 因为板上的三个测试模块没有重名的。测试模块 cmd_clash（232 B）已经打好： 它声明 uart_echo 的命令名，并且故意什么资源都不认领—— 否则加载器会先因引脚拒绝它，命令名那条路径照样不执行，通过了也证明不了任何事。 等下一次烧录后推进去，它要么让 S4 变成「已验证」，要么当场暴露。
  • A6 驱动移植脚手架未认领
    把 MicroPython / LuaTOS 的 C 驱动翻译成 MDL 形状的骨架 + 检查清单。 库的价值最终体现在「推一个 .mdl 就能用一个新器件」，而不是能不能跑别人的源码。
  • S8 解释器 MDL未认领
    化解 REPL 取舍的那个选项，但它是独立规模的工程， 建议单独立项而不是顺手做。验收另计：解释器 MDL 与原生 MDL 同时驻留， 前者崩溃时后者继续跑。
  • 不存在的 I2C 地址要等超时已知未修
    NACK 与超时现在都落到同一条等待路径上，所以扫满 112 个地址约 45 s。 功能正确，只是慢——记在这里是为了它不被悄悄忘掉， 而不是因为它挡住了什么。
  • X1 / X2 跨架构已搁置
    RV32 PIC 可行性与 ESP32-C3 集成。按"只关注 P 序列"的要求搁置，未动。

2.0 计划

  

    起点是对比表里暴露的两项差距：同时驻留（我们一次一个）与
    即写即跑（我们要过工具链）。下面先是四条分析，
    其中两条的结论是不做那件显而易见的事。
  


  

    竞品的「同时驻留」没有槽位这个概念
    MicroPython 和 LuaTOS 的模块是一个堆里的对象，同一个 VM、同一个地址空间、
    同一个特权级，数量只受 RAM 限制。而它们的无限并存恰恰来自没有隔离
    ——一个堆、一个 GC、一个特权级，模块 A 的 bug 直接破坏模块 B 的数据。
    所以对标的不是它们的数字，是我们能负担几个隔离槽位。


    核实过：MPU 区域是每任务的、切换时重编程，所以它
    不限制槽位数量。真正的约束是 2 的幂自然对齐。
  


  

    槽位数不该写死——但碎片问题有个干净解
    每个 MDL 的大小由业务复杂度决定，固定划分要么浪费要么不够。两端的先验已各有一半：
    packer 知道 text/data/bss，设备的 arena 命令知道容量，
    缺的是协商。


    整理碎片需要追踪栈堆里的指针，而追踪器要么漏指针要么过度保留
    ——那正是 GC 的工作，而我们拒绝了 GC。但那个风险来自细粒度分配，
    而我们没有细粒度分配：一个 MDL 就是一整块，整块分配整块释放，
    它的堆和栈都在块内。块外指向块内的引用只有宿主侧那几个，全部可枚举且已在
    reclaim_module() 里清除。


    而 MPU 的对齐要求反过来给了现成解：buddy 分配器。
    2 的幂对齐正是 buddy 的前提，它释放时自动合并、内部碎片有界、
    不需要追踪任何指针。唯一诚实的代价是内部碎片
    （5K 的 MDL 占 8K 块），而它可预测、可提前报告。
  


  

    库：拿不走源码，但能拿走全部值钱的部分
    它们的库是给一个我们没有的解释器用的源码。但那些库里最值钱的
    不是 Python/Lua——是底下那层 C 驱动（两者的驱动本来就是 C）和
    器件知识：寄存器映射、初始化时序、勘误规避。那些与语言无关。


    策略是 API 形状兼容而非源码兼容，让移植成为近乎逐行的机械翻译。
    用户端的落点是：装一个新器件就是推一个 .mdl，立刻能用——不重启、不重跑、不重烧。
  


  

    REPL：不做，但取舍被第四个选项化解了
    REPL 要执行没有预先编译过的代码。内置解释器等于放弃原生速度这个立论；
    而实测一次完整往返是 715 ms，差距不在速度，
    在于要人手动触发和设备上无法探索。


    第四个选项：把解释器做成一个可选的 MDL。
    它在沙箱里跑、占一份 arena、不加载时成本为零，需要速度的模块继续是原生的。
    于是这不再是全局二选一，而是逐模块选择——
    而这只有在有槽位机制的前提下才成立，所以它是多槽位的红利。
  


  

    做 S2 时发现计划的顺序排错了
    reclaim_slot() 里有一句 mdl_events_disarm_all()。
    单槽位正确；多槽位下回收槽位 A 会把槽位 B 的中断一并下掉，而且是静悄悄的。
    这不是加个参数能补的——事件层只有一个任务句柄、一个队列、一份 armed 掩码。


    我把「事件路由」（S3）排在「多槽位加载」（S2）之后，理由是前者听起来像后者的完善。
    实际是反的：没有路由，多槽位加载一落地就带着一个真实缺陷，
    而症状（某个模块的按键突然不灵）离原因很远。


    按排序准则自己的例外条款处理：改计划、记明原因，
    而不是绕过去或先欠着。S3 提前，与 S2 合并完成。
  


  

    Agent 优先重排了整张表
    如果编码主要由 agent 完成，工具链成本几乎归零——这恰恰暴露出
    那张对比表是按人类用户假设写的。真正要紧的变成机器可读的错误和机器可验证的状态。


    最关键的一点：本项目的验证纪律本身就是一个 agent 安全特性。
    「已验证」与「完成」的区分，对人是自律，对 agent 是护栏——
    它阻止 agent 把没测过的代码当成能用的。
    竞品没有这个区分，因为人会自己去试；agent 不会，除非你告诉它这里有区别。

      S0host API 需要知道调用者是谁
      
    
        四个外设驱动里的 checked_*() 全都直接读 g_mdl_slot
        单例（各 4 处）。多槽位下「这条总线是你声明的」
        必须先能回答「你是谁」。调用发生在 MDL 自己的任务里，
        xTaskGetCurrentTaskHandle() 能反查槽位——但每个 gated 入口都要过这层。
        其余任务全压在它上面。

  • 
      S1buddy 分配器
      
    2 的幂对齐是 MPU 的硬性要求，而那正是 buddy 的前提。释放时自动合并；
        粒度是「一个 MDL 一块」所以不需要追踪指针。内部碎片如实报告，不做整理。
    
    
    • 
    
  • 
      S2跨槽位资源仲裁（MDL ↔ MDL）
      
    现在的冲突只有「MDL vs host」。R3 的引脚展开语义已经是对的，
        需要的是把比对范围从一个槽位扩到全部。这是多槽位最容易出安全问题的地方：
        两个 MDL 同时驱动一根线。
    
    
    • 
    
  • 
      S3事件路由到正确的槽位
      
    host_events.c 现在只有一个 s_module_task。
        GPIO 边沿该投给声明了那个引脚的槽位，不是广播。
    
    
    • 
    
  • 
      S4–S7命令名跨槽位唯一 · 持久化一组 · 逐槽位看门狗 · status 分列
      
    都是单槽位时被隐含掉的假设，多槽位后需要显式化。
    
    
    • 
    
  • 
      S8解释器作为一个可选 MDL
      
    化解 REPL 取舍的那个选项。Lua 比 Python 小得多，是更现实的第一步。
        验收另计：解释器 MDL 与原生 MDL 同时驻留，前者崩溃时后者继续跑——
        那就同时证明了隔离和「逐模块选择语言」。
    
    
    • 
    
  • 
      W1 · W2watch 模式 · 硬件 shell
      
    W1 把 715 ms 变成无感（存盘即重建推送）。
        W2 让控制台直接调 host API：i2c read 1 0x48 2、
        spi xfer 3 9F 00 00 00——覆盖 REPL 在嵌入式上的主要用途，
        不需要解释器。
    
    
    • 
    
  • 
      A4–A6结构化输出 · MCP 暴露验证状态 · 驱动移植脚手架
      
    A5 是其中最要紧的：agent 需要能问「这个结论是真机验过的还是只是编译过」，
        而这个区分原先只以文字形式存在于 maintain.md 里。A4/A5 已验证，A6 未认领。

    
        这里我还违反过一次自己刚立的排序准则：计划排完就建议「A4/A5 不依赖多槽位，
        现在就能做」——按依赖排完序，又换一把尺子往前挑。而那个建议本身也是错的：
        A4 是给 status/pins 加结构化输出，
        而 S7 正是「status 按槽位分列」——先做 A4 等于等着被 S7 重写。
    
    
    • 
    
  • 
      内置 REPL明确不做
      
    把解释器烧进固件，等于让所有人替少数人的交互需求付性能代价。
        做成 MDL 则是逐模块选择。记为有理由的决定，不是「以后再说」。

    2.0 的验收标准，沿用本项目一贯规矩——编译通过不算：
    真机上同时跑起 ADC 采集 + SPI 记录两个独立 MDL，各自声明各自的引脚；
    第三个想抢已占引脚的 MDL 在构建期就被拒；
    并且其中一个崩溃时另一个继续运行。


    最后那条是多槽位真正的价值——也是它比单槽位难的全部原因。
